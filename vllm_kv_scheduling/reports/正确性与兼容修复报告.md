# 正确性与兼容修复记录

环境：单张 RTX 3090，Qwen3-1.7B FP16，vLLM 基础 Commit `275de34170654274616082721348b7edd9741d32`。本报告中的诊断 Run 不参与正式性能统计。

## 1. 原生部分 CPU Block 恢复

在 CPU Block=256、GPU Block=16 时，GPU 前缀可能结束于 CPU Chunk 中间。原生 0.11.2 在构造 CPU→GPU 映射时错误地处理了跳过方向，真实 W-C 测试触发 `src_sub_block_count` 断言。

适配上游 [#28951](https://github.com/vllm-project/vllm/pull/28951)：按目标 Sub-block 数计算应跳过的源 Sub-block，并按实际目标长度分配映射数组。

GPU 回归测试使用已知数值模式，验证两个 CPU Chunk 的中间区间加载到指定 GPU Blocks，随后验证 D2H。通过 `torch.equal` 检查实际数据，不仅检查没有异常。

失败日志：`/mnt/ondeviceinfer/experiments/vllm_kv_scheduling/raw/cpu-smoke-v2.log`。

## 2. Pending Store 与抢占

本版本 Scheduler 的 Pending 记录直到请求结束才批量确认。不能根据“之前提交过 Store”判断 CPU 数据已 Ready，也不能直接释放正在被搬运的 GPU 源块。

适配上游 [#29870](https://github.com/vllm-project/vllm/pull/29870) 的等待机制，并引入其依赖的下一 Step 提交 Store 行为：Worker 在覆盖被抢占 Block 前提交此前排队的 Store，并等待相关 CUDA Event；Scheduler 对应清理/确认已被保护的状态。

基线和优化组使用相同兼容补丁，未移植新的跨层搬运 Kernel，不将修复本身的影响计入调度收益。

## 3. 已预留但未执行的缓存登记

真实 KVCacheManager 复现：

| 状态 | 后续请求可探测前缀 |
| --- | ---: |
| 实际只执行到 31 Tokens | 16 Tokens |
| 预留第 32 Token，但尚未执行 | 32 Tokens |
| 直接释放请求 | 仍为 32 Tokens，包含未执行数据 |
| 回滚提前登记再释放 | 16 Tokens，保持已执行部分 |

原因是 `allocate_slots` 会提前登记本 Step 计划完成的整块 Hash。非队尾抢占若选中了本轮已预留资源的请求，仅回滚 Token Budget 不够。

本项目在该回滚分支清除超出已确认计算进度的缓存登记，保留已经有效计算的前缀，再复用原有 Block 释放。对应测试：`test_rolled_back_reservation_cannot_publish_uncomputed_kv`。

## 4. CPU 加载后恢复生成历史

原生路径在异步加载完成后，将请求状态统一设置为 WAITING。对先前被抢占的请求，这会进入 NewRequestData 分支，使 Worker 重建空的 Output Token 历史。

相同输入历史的诊断中，`C-17-00015` 在恢复后第 3 个输出位置曾出现最大 Logit 差约 12.19、RMS 约 1.87。这是实际状态错误，不能用 Batch 浮点差异解释。

修正为：被抢占过的请求完成加载后恢复 PREEMPTED 状态，走原生 ResumedRequestData 分支，保留已生成 Token。真实 Scheduler 回归测试验证输出仍带有两个已有 Token，且没有作为 New Request 发布。

修正后，同一位置的差异降至 FP16 数值量级，并完成以下完整历史核验。

## 5. 相同历史数值核验

使用同一 Trace 的 24 个请求、每个固定 64 个输出。固定 GPU 参考产生的输出历史，通过 Sampler 注入确保各路径继续输入相同 Token；对 5 个目标请求的全部 64 个生成位置保存原始 Logits，共 320 个位置。诊断阶段只在 GPU 上 Clone，Trace 结束后才传回 CPU，避免在 Forward 中加入同步拷贝。

对照包含宽松 GPU Reference、受限 GPU Pressure、CPU Baseline 和 Combined。各路径的 Worker/Core 输出历史长度也逐步核对。

| 对照参考的路径 | 位置数 | Top-1 一致率 | 最大概率差 | 最大 KL | 非近似并列候选 Top-1 变化 |
| --- | ---: | ---: | ---: | ---: | ---: |
| GPU Pressure | 320 | 99.6875% | 0.004410 | 5.79e-5 | 0 |
| CPU Baseline | 320 | 99.6875% | 0.004866 | 6.43e-5 | 0 |
| Combined | 320 | 99.6875% | 0.004389 | 6.61e-5 | 0 |

原始 Logits 最大绝对差分别约 0.156、0.234、0.242。最初使用的 0.1 原始绝对误差阈值连 GPU-only Batch/Pressure 对照也无法满足；原始失败检查保存在 `teacher_forced_quality_raw_check.json`。后续同时比较归一化概率、KL、Top-1 Margin 和独立 GPU 对照，原始差值全部保留。

概率门槛：最大概率差≤0.01，平均 KL≤1e-4，最大 KL≤1e-3，参考 Margin>0.05 时不允许 Top-1 改变。三个路径均通过。KL 使用 FP64 计算，避免接近零时 FP32 消减产生负数。

这验证了本次选定压力 Trace 的缓存/恢复路径，不代表公共数据集模型质量分数，也不要求调度改变 Batch 后的 Greedy 文本逐字一致。

原始 Tensor 与请求事件：`/mnt/ondeviceinfer/experiments/vllm_kv_scheduling/raw/teacher_forced/`。汇总：`teacher_forced_quality.json`。

## 6. Admission 机制与重算计数

真实 Scheduler 的最小资源冲突测试：Warm 前缀初始为 128 Tokens。Cold 先准入会使可复用前缀缩短为 96 Tokens；GPU-aware 先准入 Warm，则保留 128 Tokens。测试同时检查实际首个准入请求和 BlockPool 查询结果。

实际重算使用成功执行的 Token 位置区间交集：先执行 `[0,512)`，再执行 `[384,640)` 只增加 128 个重算 Tokens；再次执行 `[0,256)` 增加 256，合计 384。GPU/CPU 缓存恢复不计为模型计算。
