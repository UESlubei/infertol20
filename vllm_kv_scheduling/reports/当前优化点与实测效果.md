## 已实现的优化

1. **GPU Cache-aware Admission**：只读查询 GPU 前缀命中量，在等待队列前 8 个位置内稳定重排，优先复用现有 KV；不符合条件的请求作为屏障，不跨越已抢占、已部分执行等请求。默认 2000 ms 超时后优先保持先到顺序。
2. **Tier-aware Admission**：同时探测 GPU 命中和原生 CPU Offload 中连续 Ready 的 KV，依据实测 Prefill/H2D 成本估算可节省时间；CPU Probe 不修改 LRU、引用或搬运状态。保留 Aging 和超时优先。
3. **代价感知抢占 Recompute/Restore**：统计真实可释放的独占 GPU Blocks，优先考虑可满足当前资源缺口的候选；按可释放量/恢复代价和输出预算进度选 Victim。Recompute 使用重算成本；Restore 估计原生 CPU 恢复和剩余重算路径。支持非队尾 Victim 的 Token/Block/Hash 预留回滚。LCF、PR-score 作为独立参考对照。
4. **观测和复现**：实际执行区间账本统计真正重复执行的 Tokens，区分缓存命中、CPU 匹配、实际加载和搬运 Bytes；每 Run 保存 Trace、请求时间、Manifest 与冻结源文件哈希。

公共兼容修复同时用于基线与优化：部分 CPU Chunk 映射、抢占 Store Flush、生成历史恢复、取消时 DMA Block 保护、重复/双向完成回调、空闲轮询和已完成加载持有者推进。这些是安全与正确性支撑，不计为调度策略收益。

## 如何解释这些结果

- **当前最明确的收益来自缓存感知准入。** A/GPU 640 的 P95 TTFT 配对变化探索性 95% CI 为 [-22.31%, -15.85%]；C 联合策略为 [-17.16%, -9.40%]。但 A/GPU 1024 的延迟区间跨零，说明收益依赖缓存压力。
- **吞吐收益有限。** A 与 C 采用固定开放到达 Trace；A 的吞吐约 205～206 output tok/s，接近提供的输出负载，不能据小幅变化推断最大容量。C 联合策略吞吐变化区间 [-0.73%, +1.26%]，未确认吞吐提升。
- **有公平性取舍。** A/GPU 640 的固定 Cold 类请求平均 TTFT 增加 8.09%，GPU 1024 时增加 15.91%。整体 P95 改善不能代替分类等待检查；2000 ms 是排序优先阈值，不是延迟上界。
- **CPU 感知本身的增益需区分对照。** C 中 Tier Admission 相对 GPU Admission 的实际 Prefill 再减少 6.35%，但 P95 TTFT 配对变化 +3.05%、区间跨零；不能把 Tier 相对 FCFS 的全部收益归因于 CPU Probe。
- **代价感知抢占暂未证明优于原生策略。** B/GPU 640 的实际重复执行 Tokens 从每 Run 均值 6925.4 增至 66067.4，Prefill 增加 10.33%，伴随吞吐和延迟退化；GPU 1024 下 Prefill 仍增加，延迟区间跨零。成本估计对 GPU 前缀存活采用保守假设，进度只是预算启发式；消融未完成前不将这些假设直接认定为唯一原因。
- **多轮会话没有观测到联合收益。** D 联合策略吞吐下降 3.76%、P95 TTFT 增加 1.20%；实际 Prefill 减少 3.56% 没有转化为端到端收益。当前 D 使用固定 Token 历史和因果到达；真实生成答案写回上下文的应用示例是后续独立验证，不混入这些配对数据。
